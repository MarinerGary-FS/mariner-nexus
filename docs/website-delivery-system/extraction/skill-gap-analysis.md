# Existing Skill Gap Analysis

## Skills audited

1. `mariner-nexus-website-delivery`
2. `mariner-nexus-codex-web-engineering`

The globally installed Skills were read with all current reference files. WDS-01 makes no changes to them.

## Website Delivery Skill

### Remains correct

- strategy before interface;
- client truth and objectives before stack;
- CREATE / EVOLVE / TRANSFORM as discovery states, not packages;
- Strategy × Experience × Systems framing;
- CORE / SCOPED / OUT risk thinking;
- skim/explore architecture;
- client identity controls expression;
- interactions require meaning;
- simplest adequate architecture;
- acquisition must define post-action operation;
- approval before implementation.

### Proven incomplete

- no formal VERIFIED / CLIENT-PROVIDED / INFERRED / RECOMMENDED / REQUIRED INPUT / PROHIBITED CLAIM model;
- no publication authorization register;
- no proportional delivery tiers or independent risk modifier;
- no amplification/amplitude decision model;
- no Content Integrity architecture;
- no accumulated-system release certification;
- no explicit client/internal/owner approval separation;
- no change-control classes;
- no recurring-cost protection;
- approval gates stop before revision, promotion, smoke, rollback, and handoff.

### Obsolete or risky

- the fixed twelve-stage workflow is too linear and front-loaded for small projects;
- the acceptance reference has only eight broad questions and does not classify always/conditional/advisory gates;
- `Next.js App Router + TypeScript + Vercel + GitHub` is presented too close to doctrine rather than a replaceable default;
- project classification mixes service/scope risk with delivery depth.

### Recommended revision

Keep one orchestration Skill. Move detailed lifecycle, truth, approval, tiers, amplification, change control, and QA matrices into focused references. The master Skill should route among them based on project profile and current gate, not reproduce every reference inline.

## Codex Web Engineering Skill

### Remains correct

- approved specification outranks convenience;
- server/static defaults and small client islands;
- dependency restraint and explicit escalation;
- mobile-specific choreography;
- accessibility, performance, fallbacks, and no silent compromise;
- bounded briefs, reviewer roles, validation, and completion reporting.

### Proven incomplete

- no machine-readable project profile or QA manifest;
- no truth/publication enforcement contract;
- no route/status/metadata/redirect/secrets automation model;
- no Content Integrity reference or state-matrix generation;
- no release-candidate certification and promotion/rollback playbook;
- no integration contract for persistence-before-notification and environment isolation;
- no owner-protected action list;
- completion report lacks authorization, truth, operational state, remote divergence, and release identity fields.

### Obsolete or risky

- hard-coded Next.js-oriented defaults need a provider/framework decision boundary;
- the fixed eight implementation phases describe Mariner's build order more than a universal engineering lifecycle;
- “run all tests” needs a generated, tier-aware QA contract;
- builder/reviewer/QA roles are useful but must not imply parallel agents are always needed.

### Recommended revision

Keep one engineering Skill. Add references for project-kernel consumption, server/client and progressive-enhancement review, Content Integrity, integrations, release certification, deployment/rollback, and completion evidence. Keep framework-specific material in references or adapters.

## Recommended Skill architecture

### Master Skill: keep and revise

`mariner-nexus-website-delivery`

Owns process, proportional rigor, current lifecycle stage, truth, scope, approvals, change control, evidence, and client/owner boundaries.

### Engineering Skill: keep and revise

`mariner-nexus-codex-web-engineering`

Owns technical implementation, progressive enhancement, accessibility, responsive behavior, performance, security, testing, and deployment mechanics.

### Focused references—not separate Skills initially

- intake and discovery;
- truth and publication authorization;
- identity translation and amplification;
- project profile and QA manifest;
- Content Integrity;
- integration contracts;
- release certification and rollback;
- client review and change control.

Create a separate Skill only if a module later proves independently invocable, requires distinct tooling, and can be maintained without duplicating orchestration doctrine.

## Remove or retire later

- copied Mariner-specific repo template in `mariner-nexus-delivery-system/`;
- duplicated local Skill copies after canonical installed Skills are revised;
- fixed Mariner redesign file names in generic bootstrap guidance;
- any default that imports Mariner colors, typography, routes, Nexus, Thread, takeover states, or phase numbering.
