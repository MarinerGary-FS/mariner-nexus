# Reference Implementation Audit

## Audit scope

WDS-01 reviewed the root operating rules; canonical redesign doctrine; decision history; Phase 00–08 and EA-01–EA-07 plans and completion reports; ARC-01; operations; current and historical bootstrap material; installed Website Delivery and Codex Web Engineering Skills and references; package/build configuration; routes; server/client boundaries; design primitives; navigation; Work registry and identity profiles; inquiry adapters/tests; SEO/sitemap/robots; Content Integrity tooling; release evidence; and the pre-existing delivery-system package.

## What made delivery successful

The decisive factor was not Next.js, a visual system, or a phase count. Success came from a controlled chain:

1. Canonical doctrine separated approved strategy from superseded material.
2. Bounded plans translated intent into testable implementation contracts.
3. Decision records prevented settled choices from reopening silently.
4. Server-rendered meaning survived optional interaction layers.
5. Responsive behavior was authored as reorganization, not shrinkage.
6. Truth and authorization controls prevented unsupported publication.
7. Human visual review and automated geometry checks complemented each other.
8. Each advanced experience had explicit meaning, access, performance, and fallback boundaries.
9. Preview review and accumulated-system certification preceded Production approval.
10. Rollback, inquiry operations, and post-promotion smoke made delivery operationally complete.

## Architecture findings

### Strong reusable candidates

- repository-relative doctrine and durable decision history;
- strict typed implementation with server-first/static defaults;
- small semantic layout and control primitives;
- scoped configuration contracts for identity, metadata, routes, and integrations;
- progressive enhancement, reduced motion, keyboard, and JavaScript-free meaning;
- typed validation and dependency-injected operational services;
- generated route/viewport/state QA matrices;
- evidence-backed Preview, release certification, promotion, rollback, and smoke playbooks.

### Configurable rather than universal

- stack/provider selection;
- route model and navigation composition;
- type, color, spacing, breakpoint, motion, and amplitude systems;
- CMS/data/inquiry/analytics choices;
- portfolio authorization models;
- browser depth, failure simulation, and performance thresholds by risk.

### Evidence only—not defaults

- Mineral Teal and Mariner environmental palette;
- Geist/Source Serif pairing;
- Mariner Thread, Systems deconstruction, Nexus, Range, and the 2→6→8.5→10→1→2 curve;
- Undugu, Serene, Sovereign, Awakening, and Gary identity rules;
- Google Sheets/Resend inquiry implementation;
- Mariner route names and case-study narrative.

## Pre-existing delivery-system finding

`mariner-nexus-delivery-system/repo-template/` copies the Mariner redesign path, Mariner-specific AGENTS doctrine, all nine Mariner specification documents, and a Mariner Phase 01 plan. This violates the intended distinction between reusable standards and reference expression. Its two bundled Skills are close copies of the globally installed Skills and lack the later truth, Content Integrity, accumulated-system certification, cost, and approval architecture proved in Production.

Recommendation: quarantine it as historical evidence during WDS-02, then replace it only after the Validated Project Kernel proves a neutral bootstrap. Do not incrementally polish it into the new system.

## Historical lessons

- Phase-by-phase approval was necessary but insufficient; ARC-01 found cross-route accessible-name, contrast, and initialization defects.
- A responsive screenshot selector demonstrated states but did not prove a living responsive interface; later work corrected the architecture.
- Content could be inside bounding boxes yet still look wrong; human typography review remained mandatory.
- A strong project could dominate a portfolio unintentionally; hierarchy needed whole-system review.
- Advanced 3D was considered and rejected because DOM/SVG already communicated the model.
- Production inquiry success depended on operational ordering and environment isolation, not form polish.
- Speed Insights was useful as a recommendation but not justified as a paid checklist purchase.

## Confidence

High confidence: doctrine, truth, authorization, progressive enhancement, responsive integrity, release control, rollback, cost approval, and QA complementarity.

Medium confidence: exact delivery tiers, project-profile serialization, browser coverage by tier, and which integration adapters deserve first-class WDS references. These require pilot evidence beyond one production repository.

Low confidence / unresolved: commercial tier pricing, maintenance packages, mandatory CMS/provider choices, regulatory profiles, and client-review tooling. WDS-01 does not decide these.
